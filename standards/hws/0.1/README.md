# Hardware Write Safety (HWS) 0.1

Working draft 0.1. Not a certification. It makes no SIL or PL claim.

HWS is a working standard for agents that write to physical hardware. It lists requirements, each with an ID, a level (MUST or SHOULD), a rationale, the standards and ideas it borrows from, and how it is verified. The machine-readable list is [`requirements.toml`](requirements.toml): 56 requirements (50 MUST, 6 SHOULD) in 13 areas.

## What it covers

- Hazard classes: every actuating action has a class, computed by code, with an unknown meaning most restricted and a class that is never offered.
- An independent safety function: separate hardware that the planner cannot talk to or around, with an independent watchdog and latched faults.
- Approval leases bound to the exact action and state: single-use, short-lived, signed, and created by a physical act.
- A liveness heartbeat: a challenge with a fresh nonce, with loss meaning power off within a stated time.
- Outside-text isolation: text from the world is typed, fenced and inert, and a taint latch limits what can happen after it.
- Provenance and trust of facts: origin and tier assigned by the host, expiry, and no hazardous action resting on a device's own report.
- Guarded buses: a guard outside the planner's domain forwards only the byte-identical approved frame.
- Evidence: tamper-evident records and an evidence pack for any claim.
- Proof tests: regression checks, fuzzing, an adversarial catalog and proof tests of the installed safety path.
- Physical controls: arm switch, update jumper and personal lockout.
- Firmware integrity: countersigned releases, signed boot and a pinned build chain.
- Human factors: prompts generated by the gate, scarce approvals, and a visible armed state.

Area codes: CLS classification, APR approval and leases, ISF independent safety function, HBT heartbeat and liveness, STP safe state and stops, BUS bus and command guarding, PRV provenance and trust of facts, TXT outside-text isolation, LOG logging and evidence, TST testing and proof tests, PHY physical controls, UPD update and firmware integrity, HUM human factors.

## Status

HWS 0.1 is a working draft. It has had no review outside the author's companies. It is not a certification, it is not a conformance scheme, and it makes no SIL or PL claim: the planner is untrusted software, and only the safety function could ever claim anything, after an assessment this project has not had. Requirement text is our own wording. ISO, IEC and UL standards are cited by name and clause topic only, as the concepts a requirement borrows from; no text is copied from them, and they have not all been read in full (the research record lists which were not).

Each requirement has no status field. Status is computed elsewhere, from requirement records that cite these IDs; the table below is a hand-maintained snapshot until that exists.

## How it relates to MHS and MWS

- **Model Hardware Standard (MHS)** is Anthropic's research-preview standard for hardware drivers. MHS describes the device and its limits. HWS governs whether and how an agent's write may reach the device. They are complementary: an MHS description is the kind of fact an HWS gate consumes, at the trust tier HWS assigns it.
- **MCP Write Safety (MWS)** covers software writes through MCP servers. HWS follows its style (IDs by area, MUST and SHOULD, one sentence per requirement) and covers writes that move energy.

Disclosure: HWS and MWS share an author; Sawbones Labs and IsoKron share a founder.

## Versioning

- Versions are semantic (`0.1`, `0.2`, `1.0`). Each version lives in its own folder under `standards/hws/<version>/`.
- IDs are never reused and never renumbered. A removed requirement stays in the file, marked `withdrawn_in = "<version>"`; it is never deleted.
- A change to requirement text bumps the version and adds an entry to [`../CHANGELOG.md`](../CHANGELOG.md).
- A version is released when `standards/hws/<version>/RELEASED` exists. The file lists a SHA-256 for every other file in the folder. A released folder is immutable: `ci/check_standards.py` fails on any change to it. Fixes go into the next version.
- 0.1 is a working draft and has no `RELEASED` file, so it can still change. Changes to the draft are still recorded in the changelog.

## Record format

Each `[[requirement]]` in `requirements.toml` has:

| Key | Meaning |
| --- | --- |
| `id` | `HWS-<AREA>-<n>`, stable |
| `area` | the three-letter area code in the ID |
| `level` | `MUST` or `SHOULD` |
| `title` | a short name |
| `text` | the requirement, one or two sentences |
| `rationale` | why it exists |
| `borrows` | source concepts, by name only |
| `verify` | a list drawn from `test`, `analysis`, `inspection` (fuzzing counts as test) |
| `version_added` | the version that introduced it |
| `withdrawn_in` | optional; set when a later version withdraws it |

## Proposing changes

Open an issue or a pull request against `rafe-walker/sawbones-labs`. A change to anything under `standards/` is a protected-path change: it needs the `guards-change` label and the clean-room reviewer. Say which ID is affected, what changes and why, and which source concept it rests on. New requirements get new IDs. A reviewer outside the author's companies is wanted; say so in the pull request if you are one.
